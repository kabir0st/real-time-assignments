7. Which task, i.e., computePower and computePrimes, executes first, and why?

## Answer

**`computePrimes` executes first.**

## Detailed Explanation

### The Code
```c
int main() {
    piface_init();
    piface_clear();

    piface_puts("DT8025 - A3P1");
    RPI_WaitMicroSeconds(2000000);
    piface_clear();

    spawn(computePower, 0);     // Line 96 - Creates thread
    computePrimes(1);           // Line 97 - Direct function call
}
```

## Why computePrimes Executes First

### Key Difference: spawn vs Direct Call

**Line 96: `spawn(computePower, 0)`**
- Creates a **thread** that will run `computePower`
- Thread is added to `readyQ` (waiting to execute)
- `spawn()` **returns immediately**
- `computePower` does **NOT** execute yet
- Thread waits for scheduler to dispatch it

**Line 97: `computePrimes(1)`**
- **Direct function call** (not spawned as a thread)
- Executes **immediately** in the main context
- Runs right after `spawn()` returns
- No scheduling involved - just a normal function call

## Execution Timeline

```
Time 0: main() starts
├─ piface_init()
├─ piface_clear()
├─ piface_puts("DT8025 - A3P1")
├─ RPI_WaitMicroSeconds(2000000)
└─ piface_clear()

Time 1: Line 96 - spawn(computePower, 0)
├─ DISABLE interrupts
├─ Initialize thread system (first spawn)
├─ Dequeue Thread 0 from freeQ
├─ Configure: T0.function = computePower, T0.arg = 0
├─ Create context with setjmp (returns 0)
├─ Setup stack
├─ Enqueue Thread 0 to readyQ
├─ ENABLE interrupts
└─ spawn() RETURNS (computePower NOT running yet!)

Time 2: Line 97 - computePrimes(1) ← FIRST TO EXECUTE
├─ Direct function call
├─ Enters computePrimes immediately
├─ for(int n = 0; ; n++)
├─   if (is_prime(0)) → false
├─   if (is_prime(1)) → false
├─   if (is_prime(2)) → true!
└─     PUTTOLDC("T1: Prime 2\n")    ← First output!
      RPI_WaitMicroSeconds(500000)
      yield()                        ← First yield

Time 3: First yield() in computePrimes
├─ DISABLE interrupts
├─ readyQ is not NULL (has Thread 0)
├─ p = dequeue(&readyQ)              → p = Thread 0
├─ enqueue(current, &readyQ)         → main/computePrimes queued
├─ dispatch(Thread 0)
├─   Save main context
└─   longjmp to Thread 0 context

Time 4: Thread 0 (computePower) starts ← SECOND TO EXECUTE
├─ longjmp returns to spawn's setjmp
├─ setjmp returns 1 (not 0!)
├─ ENABLE interrupts
├─ current->function(current->arg)   → computePower(0)
├─ Enters computePower
├─ for(int n = 0; ; n++)
├─   PUTTOLDC("T0: 0^2=0\n")        ← Second output!
└─   RPI_WaitMicroSeconds(500000)
    yield()
```

## Queue States

### After Line 96 (spawn returns):
```
readyQ: [T0: computePower] → NULL
current: main (running)
```
computePower is **queued**, not running.

### Line 97 executes:
```
computePrimes(1) executes in main context
↓
Enters loop, finds prime 2
↓
Prints "T1: Prime 2"        ← FIRST OUTPUT
↓
Calls yield()
```

### Inside first yield():
```
Before dispatch:
readyQ: [T0: computePower] → NULL
current: main/computePrimes

After dequeue:
p: T0 (computePower)
readyQ: NULL

After enqueue:
readyQ: [main/computePrimes] → NULL

After dispatch:
current: T0 (computePower NOW RUNNING)
```

### computePower starts:
```

↓

↓

```

## Comparison: spawn vs Direct Call

### spawn(function, arg)
```c
spawn(computePower, 0);
// - Creates thread
// - Adds to readyQ
// - Returns immediately
// - Function doesn't execute yet
// - Needs scheduler/yield to start
```

### Direct Call
```c
computePrimes(1);
// - Executes immediately
// - Runs in current context
// - No thread creation
// - No scheduling needed
// - Blocks until yield() or return
```

## Why This Design?

This pattern is intentional:

1. **spawn creates a background task**
   - computePower runs concurrently
   - Won't block main execution

2. **Direct call runs main work**
   - computePrimes is the "main" work
   - Runs immediately
   - Controls when to yield to other threads

3. **Cooperative scheduling**
   - computePrimes decides when to share CPU
   - Calls yield() after each prime
   - Allows computePower to run

## Alternative Scenario: Both Spawned

If line 97 was also a spawn:
```c
spawn(computePower, 0);   // Thread 0
spawn(computePrimes, 1);  // Thread 1
// main() would return immediately
// Neither would execute (no yield in main)
// System would end!
```

## Alternative Scenario: Neither Spawned

```c
computePower(0);   // Infinite loop!
computePrimes(1);  // Never reached
```
- computePower runs forever
- computePrimes never executes
- No concurrency

## Key Reasons Summary

**computePrimes executes first because:**

1. ✅ **It's a direct function call** (line 97)
2. ✅ **Executes immediately** after spawn returns
3. ✅ **No scheduling delay** - runs in main context
4. ✅ **spawn only queues** the thread, doesn't execute it
5. ✅ **computePower waits** in readyQ until first yield()

## The Answer

**`computePrimes` executes first** because:
- It's called directly, not spawned
- Direct calls execute immediately
- spawn only creates a thread (doesn't execute it)
- The spawned computePower thread waits in readyQ until computePrimes calls yield()

This is a fundamental difference between **thread creation** (spawn) and **function execution** (direct call).
